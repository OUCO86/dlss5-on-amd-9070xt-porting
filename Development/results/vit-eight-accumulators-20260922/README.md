# ViT八累加片段：A/B重用、循环展开与驻留容量

2026-09-22，接续32×32平衡tile研究。原核16×64使用四个累加片段；本轮16×128和32×64均八个片段、每完整wave2048个输出，M640时同为1280个wave（原核2560）。矩阵/激活/FP8舍入顺序保留；M400尾块单独BM1，不做无用矩阵计算。基线56d11ef，只有实验生成器与测试模块，没有生产改动。

## 1. 八累加器的两种取数比例

16×128每K16为A1/B8，32×64为A2/B4；逻辑密度分别28.44、42.67 FLOPs/字节，原核25.6。两种形状交叉A行布局和片段布局，真实block31的M400/640输入/权重。每项两轮ABBA，约100ms预热/400ms计时/槽。

| 配对（u4） |1080 μs|900 μs|
|---|---:|---:|
|原核→16×128行|35.665→38.790|25.522→27.221|
|原核→32×64行|36.085→40.183|25.523→24.090|
|行布局：16×128→32×64|38.958→40.336|27.324→24.274|
|片段布局：16×128→32×64|38.648→33.805|25.363→21.850|
|16×128：行→片段|37.371→36.865|24.966→25.401|
|32×64：行→片段|38.633→32.749|23.039→21.781|
|打包+矩阵：生产→片段16×128|39.763→41.094|25.983→24.475|
|打包+矩阵：生产→片段32×64|39.866→36.609|25.987→23.396|

偏向重用A的16×128并没胜过原核；更高密度32×64仍依赖A布局。1080的32×64布局配对中核心2646→2637.5MHz、显存均2238MHz，布局收益不靠更高核心时钟。900若干组显存档位不同，不能直接拿跨组绝对数字排序。

## 2. 少展开、少寄存器，不保证更快

保持形状/布局，只将K循环展开4份改2份；主计算量和累加顺序相同。

| u4→u2 |1080 μs|900 μs|
|---|---:|---:|
|16×128行|39.001→43.499|25.388→27.929|
|16×128片段|38.741→40.509|25.092→27.167|
|32×64行|39.886→36.965|22.765→23.373|
|32×64片段|32.725→33.232|22.613→20.657|

32×64/u2的打包+矩阵对原路径：108039.563→35.538μs（-10.17%）、90026.003→21.765（-16.30%）。1080核心2522.5→2692MHz、显存2238→2505MHz，这个组合百分比并非纯代码/同频收益。不同形状、布局和尺寸对展开因子的偏好不同，不能用“少寄存器”单变量解释。

## 3. 三种资源读数分开核对

实际HSACO的AMDGPU MsgPack metadata、单独生成的汇编寄存器数、HIP `hipFuncGetAttribute(NUM_REGS)`逐项一致，排除了看错模块/只看错汇编旁文件这一可能。

| 核 |VGPR|编译器Occupancy|HIP API返回wave/MP上限|
|---|---:|---:|---:|
|原16×64|77|16|64|
|16×128行/u4|136|10|44|
|16×128片段/u4|136|10|44|
|32×64行/u4|119|12|44|
|32×64片段/u4|122|10|48|
|16×128行/u2|118|12|44|
|16×128片段/u2|117|12|44|
|32×64行/u2|103|12|56|
|32×64片段/u2|104|12|56|

全部LDS0/scratch0；API报告32 MP、wave32。注意编译器Occupancy与HIP API上限不是简单乘4关系，寄存器降低也不保证该API上限升高；此不一致尚未解释，不据此推导物理驻留粒度，也不把任一数字当动态活跃率。16×128的VGPR降低但API上限不变、执行还变慢，是实际反例。32×64片段的API容量提高，但1080仍微慢，900更快；容量更高仍非提速充分条件。

## 4. 整网：仍不足以采用

每帧把8次pack换片段布局、8次expand换32×64；分别测u4/u2，各两轮ABBA、40帧预热/200计时。两档32槽共6400计时帧，候选每槽3200次替换、基线0。每槽完整原始FP32同。

| 案例 |基线→候选ms|变化|
|---|---:|---:|
|1080/u4|17.909353→17.909381|约0%|
|1080/u2|18.042420→18.026055|−0.091%|
|900/u4|12.790733→12.777526|−0.103%|
|900/u2|12.806486→12.802083|−0.034%|

显存均2505MHz，核心配对差小（完整记录见summary.json）。收益量小于槽位漂移，未建立稳定整网改善，不采用；也不能断言真实收益严格为零。热重复微段组合快8～16%不能直接外推整网。

## 验证与下一步

两批208微槽，每槽反码填充、预检及后检完整输出同；4进程首尾8次原始网络FP32同。整网32次原始FP32同，总40次，替换数正确。两个模块均gfx1200/gfx1201编译，仅gfx1201实跑；只读ADL，未调频/电压/功耗。原始CSV/遥测/哈希/资源查询均保留。

当前大缺口依然不能只归到逻辑带宽、累加器数量或寄存器容量。下一步优先把pack+expand段放在真实网络前序之后，用稀疏GPU事件量配对，并同时做不插事件的整网控制来量测量扰动。比较热重复与真实时序下的收益，区分“段内仍有小收益但总占比太小”与“换了缓存/调度环境收益消失”。另需审计编译器/运行时驻留上限的非单调差异，未弄清前不拿这组上限直接解释周期占比。
