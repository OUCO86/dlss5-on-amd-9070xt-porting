# 算力缺口：相同读取量，地址分布如何改变供数背压

2026-09-22，RX 9070 XT / gfx1201。接续 [权重访问集合扫描](../wmma-feed-gap-20260922/README.md) 的非单调曲线，本轮固定逻辑集合与计算，只改变权重块物理间距。结果支持地址分布影响供数背压，尚未定位具体缓存冲突，也未解释整网缺口。没有生产改动。

## 对照与校准

沿用合成 FP8 1/16 数据，M640/N4096/K1024、2560 wave，每 wave 256 条 WMMA，共 5.36870912 GFLOP；省去激活和原网络输出，所有累加分量进入每 lane 校验和。A 保持完整。B span64/128/1024 分别访问 256KiB/512KiB/4MiB 不同元素。

所有条件使用同一 4.25MiB B 分配。块间距从 16384 字节增加 64/128/256/512/1024 字节，空隙不读取。逻辑元素数量、加载条数、计算量不变；物理地址、页足迹与请求分布会改变，因此不能假定硬件实际传输字节数完全相同。

正式间距对照共用 `pitched4` 机器码：77 VGPR、LDS/scratch 均零，完整循环 20 条 `global_load_b64`、16 条 WMMA。增加运行时地址间距参数本身改变了代码，须先校准：

| span | 旧 masked4 μs | 新 pitched4、无空隙 μs |
|---|---:|---:|
| 64 | 48.904 | 48.303 |
| 128 | 30.944 | 28.530 |
| 1024 | 35.931 | 31.757 |

这些跨入口变化不归入间距效果。以下只在同一新入口中比较。

## 间距确实改变慢点，但完整集合改善很小

每项两轮 ABBA，约 100ms 预热，10 个计时块合计约 400ms；沿用计时外显存搬运调理，按计时窗口关联只读遥测，不使用短段 HIP 事件。各行是独立配对，单位 μs：

| 增加间距 | span64 基线→改变 | span128 基线→改变 | span1024 基线→改变 |
|---|---:|---:|---:|
| 64B | 48.201→23.278 | 28.703→25.729 | 31.778→34.116 |
| 128B | 48.194→22.441 | 28.851→24.517 | 31.815→32.475 |
| 256B | 48.240→22.249 | 28.947→24.292 | 31.761→31.114 |
| 512B | 48.312→22.135 | 29.127→24.331 | 31.784→31.186 |
| 1024B | 48.310→22.230 | 29.248→25.030 | 31.802→32.811 |

span64 加 256B 后大幅加快，核心中位数却从 3176 降至 2902MHz，显存中位数均 2505MHz，不能用升频解释。span128 改善较小；完整 4MiB 在同一对照中只少约 0.65μs，另一些间距还变慢。特殊小集合的结果不能外推成真实 ViT 翻倍。

## 纯 HIP 捕获：高命中率仍伴随等待

另以 Radeon GPU Profiler 捕获 span64/1024、间距16384/16640 四种情况。每次在第3000次 dispatch附近捕获64次调用，持续热重复；这与上述调理、分块壁钟测试是不同运行状态，不混算耗时或周期。

| span / 间距 | L0命中率 | L2命中率 | Memory unit stalled |
|---|---:|---:|---:|
| 64 / 16384 | 84.167% | 99.975% | 39.537% |
| 64 / 16640 | 85.809% | 99.971% | 18.821% |
| 1024 / 16384 | 54.758% | 99.963% | 39.823% |
| 1024 / 16640 | 55.100% | 99.962% | 37.748% |

比例按底层计数加权，非逐样本百分比平均。四份记录分别有2258、2255、2418、2407个样本，间隔4096；`ratio_checks`重建误差至多约1.42e-14。span64 的停顿指标大降，L2命中几乎不变；完整集合两者变化均小。命中说明数据在哪里被找到，不保证请求立即得到服务。

## 接回真实 ViT 原核：供数背压不只存在于合成模型

随后使用正式 `selected-modules`、冻结的真实1080输入和原权重，将第一次 `vit_expand_blocked_fp8_frag_bytein` 重复10000次，在第3000次附近捕获64次 dispatch。无捕获控制运行2帧、捕获运行1000帧，两组首尾原始网络FP32检查均为 `bitdiff=0`。

| 真实核计数器 | 加权读数 |
|---|---:|
| L0 cache hit | 57.826% |
| L2 cache hit | 99.947% |
| Memory unit busy | 94.931% |
| Memory unit stalled | 68.404% |
| Write unit stalled | 0.043% |

[真实核记录](real-vit-1080.json)有1452个样本，间隔4096，比例重建误差至多约1.42e-14。真实输入、权重和完整算子仍显示高供数停顿，为真实核受供数背压限制提供了比合成模型更直接的支持。L2几乎全命中，说明在此捕获状态下，不能仅以反复从DRAM读取解释限制；还可能涉及命中后的服务吞吐、请求分布、在途请求和依赖。

这是额外热重复的原核，不是自然整帧时序；68.4%不是整网耗时占比，也不是矩阵单元闲置比例。与合成捕获的百分比不能直接相减归因，尚未定位具体L0/L2存储体、端口或其他内部瓶颈。复现工具为实验目录的 `prepare-real.py` / `capture-real.ps1`。

## 验证与解释边界

144个计时槽，每槽 pilot 与计时后各检查一次全部 lane 校验和，均通过；不是逐次启动检查，也不是原网络输出。四次捕获各三次校验全同，无性能捕获控制也有三次通过。双架构编译，实际运行 gfx1201。

相同依赖链、计算与逻辑读取数量，换地址间距就改变执行时间及供数停顿，反对仅用依赖链或总逻辑字节解释慢点。它可能涉及缓存映射、地址转换、请求分布或服务能力，尚不能点名某级缓存的组/存储体冲突。计数器约40%的读数也不是整网40%的时间分账。

本轮把“访问多少”与“放在哪里”分开了一步。原先小集合反而慢，可以怀疑容量，也可以怀疑地址分布；如今保持元素数不变，慢点随间距移动，纯容量解释已不足。但间距也改变了物理页覆盖和请求落点，几个候选机制仍绑在一起，不能把这一对照包装成已识别硬件内部结构。完整集合的结果尤其重要：它没有出现同样的大幅变化，说明解释特殊慢点与解释原核剩余缺口仍是两件待连接的事。没有测到的矩阵利用率与各级服务带宽不补猜数。

真实原核计数器这一步已完成。下一步分开缓存命中后的服务吞吐、请求分布、在途请求数量与依赖限制，优先解释完整4MiB为何仍受限，不把特殊span64的填充当优化方向。
