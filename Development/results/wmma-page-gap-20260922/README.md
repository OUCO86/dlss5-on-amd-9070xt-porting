# 算力缺口：固定高位地址后，请求分布仍会改变供数

2026-09-22，RX9070XT/gfx1201。接续块间距实验，分开高位地址变化与块内分布。另将真实ViT捕获的请求数与逐指令地址账本对齐。两条证据用于解释缺口，没有新增生产优化。

## 固定高位，不假定硬件页或银行结构

新 `xor4` 将块内偏移替换为 `off XOR ((tile*256)&mix)`，只动bit8～11。基址4KiB对齐经过运行时检查，逐访问 `addr>>12` 不变；每次8字节读取仍对齐连续。CPU穷举16组，检查高位、唯一集合与无碰撞，见 [address-check.json](address-check.json)。这里的4KiB是地址分组，不据此推断GPU实际页大小。

同一机器码77 VGPR，完整循环20条64位加载、16条WMMA，矩阵规模和计算量不变；仍是合成1/16校验和诊断。新旧入口先校准：span64为48.364→48.234μs，span1024为32.098→31.977μs，不混入下表同入口异或效果。

| mix | span64 基线→异或 μs | 完整span1024 基线→异或 μs |
|---|---:|---:|
| 256 | 48.251→48.250 | 31.890→31.508 |
| 512 | 48.183→48.296 | 31.841→32.325 |
| 768 | 48.281→48.363 | 31.788→32.307 |
| 1024 | 48.215→25.342 | 31.774→31.945 |
| 2048 | 48.317→48.285 | 31.738→31.716 |
| 3072 | 48.311→25.411 | 31.697→31.764 |
| 3840 | 48.170→25.872 | 31.676→31.113 |

span64前三种仅在原1KiB内置换，精确集合不变，仍约48μs；引入bit10后移到同一4KiB内其他1KiB区域，变为25～26μs。只动bit11没有同样效果。高位访问序列、不同元素数未变，换了不同4KiB区域或容量不是充分解释；但不能给bit10命名为硬件银行选择位。完整4MiB始终是同一精确集合的置换，变化很小，特殊慢点仍不代表真实完整核的主要缺口。

## 捕获保留不一致，不挑选支持结论的数字

三次纯HIP捕获各64次dispatch、各三次校验和通过。加权计数如下：

| mix | L0命中率 | 内存单元停顿 | GPU busy cycles |
|---|---:|---:|---:|
| 0 | 84.295% | 39.296% | 9135941 |
| 1024 | 86.510% | 20.267% | 9173945 |
| 2048 | 82.567% | 63.343% | 6190515 |

三组L0请求均为251822080，样本2255/2273/1545，比例重建通过。bit11组捕获停顿升高，独立壁钟却未变；其busy cycles也明显不同，不能当同频同状态对照。捕获是热重复，既不与独立计时混算，也不将停顿指标当整网时间占比。

## 真实核的请求数，可以逐项算回来

[请求账本](request-account.json)按每条指令触及的128B区域计数，不按唯一地址去重。每wave读取A覆盖1024个区域、B覆盖512个；真实尾部窄写覆盖64个，合成校验和写仅1个。

真实核：`64×2560×(1024+512+64)=262144000`，与上一轮真实ViT捕获的L0请求完全一致；合成核换成尾部1，得到251822080，也一致。

| 每次真实核 | 逻辑读写载荷 MiB | 请求覆盖口径 MiB |
|---|---:|---:|
| 读A | 40 | 320 |
| 读B | 160 | 160 |
| 尾部写 | 2.5 | 20 |
| 合计 | 202.5 | 500 |

读取合计200MiB、覆盖480MiB；L2请求覆盖约210.878MiB，工具Fetch size项约0.153465MiB。覆盖数是请求数乘128B，**不是实际传输字节，更不是500MiB DRAM流量**。A的分散访问放大了覆盖口径，但不能把八倍覆盖说成八倍速度损失；此前A连续布局收益很小，说明请求数不等于关键路径。

这份账本把两个层次分开了。源码需要哪些数，决定逻辑载荷；一次指令的各线程地址分散到哪些区域，决定这里统计的请求覆盖。不同指令即使再次碰到同一区域，也会重复记账；数据是否已经在缓存中，则是下一层的问题。因此请求总数相等，不代表服务时间相等，也不代表最终去显存的次数相等。三组异或的请求总数一致而性能不同，正好提醒我们继续看分布与时序。

地址对照也有明确边界：小集合改变第十位时，精确地址集合已经改变，只保持不同元素数与高位序列。不能把它写成“完全相同地址集合也加速一倍”。只有完整集合的所有异或都保持精确集合，而那一组没有出现大幅变化。到这里，我们缩小了特殊慢点的原因范围，也量清了真实核的请求口径；距离解释真实核为何离寄存器峰值仍远，还差服务过程本身的对照。

## 官方口径与下一组问题

[RGP手册](https://gpuopen.com/manuals/rgp_manual/events_windows/)给出L0/L2请求的128B口径，并说明RDNA4的L1不实际缓存；内存单元停顿也不是整网占比。[RDNA4 WMMA指南](https://gpuopen.com/learn/wmma-guide-amd-rdna-4-gpus-part-2/)指出FP8每线程8元素通常对应64位读取，可组织128位读取。这给请求宽度对照提供依据，不保证翻倍；其INT8示例的数值论述不能照搬到浮点累加顺序。[ROCm上限说明](https://rocm.docs.amd.com/projects/rocprofiler-compute/en/docs-7.14.1/conceptual/rdna/system-speed-of-light.html)是RDNA3.5启发式缓存上限，不套算9070XT精确峰值。

下一步围绕真实完整权重，保持数学输出约束，对照请求宽度、发射组织与命中后的服务能力，分开请求数量、并发和依赖限制，不继续追特殊span64的地址技巧。
