# 本轮网络算力消耗调查汇总

截至 2026-09-21 22时这批，计划中的 C32 主干/输入/尾部和 ViT FFN 真实尺寸台阶已完成。这里汇总已支持的判断；中间其他通道层没有全部细拆。

## 已量清的范围

| 层次 | 观察 | 证据 |
|---|---|---|
| 硬件寄存器峰值 | 稠密 FP8 405.28TF、FP16矩阵204.30TF、FP32双发射49.92TF，与现有时钟下参考峰值接近 | [算力程序](../gpu-throughput-20260921/report.md) |
| 正常纯HIP整网 | 900/1080约12.86/18.30ms；已验证稀疏事件开销很小，密集逐核事件会额外拖慢约10ms | [整网区段](../network-timeline-20260921/report.md) |
| C32区段 | 约4.405/6.444ms，占本轮分段账约35%；调用次数少不代表便宜 | 同上 |
| C32内部 | 主干七项与输入/尾部均完成保持输出的受控重复；N=1校准揭示部分探针扰动明显 | [主干](../c32-phase-cost-20260921/README.md)、[输入/尾部](../c32-edge-cost-20260921/README.md) |
| ViT FFN | 真实M400/640，完整展开约101/94TF，收缩约135/148TF；去掉尾部后仍远低于寄存器峰值 | [FFN台阶](../vit-ffn-ladder-20260921/README.md) |

## 现在的解释

显卡的矩阵计算峰值确实能达到。网络的主矩阵FLOPs除整网时间只有约55TF，是把读取、转换、归一化、残差、同步和输出都放进同一个分母后的有效吞吐，不能据此说硬件只用了七分之一、还可直接提速七倍。

目前看到的是两类不同缺口：C32是许多小矩阵与大量辅助工作融合在一起，实际汇编已经有双发射；ViT大矩阵即使去掉激活/最终编码，仍不能靠现有访存/调度方式接近寄存器峰值。二者需要不同的优化方向，尚未发现一个解释全部耗时的统一开关。

C32输入和尾部并非零成本，重复实验已能观察到增量；但输入探针包含额外同步，部分探针改变寄存器和调度，RGB重复还呈现非线性。因此这些数字只适合筛选调查方向，不画成加起来100%的阶段饼图。

FFN展开在900去掉尾部能少约3.6μs，1080基本持平；补成等价拆分流程却分别多约3.8/13.3μs。收缩去掉末端舍入只差约0.3/0.6μs，拆分也更慢。展开FP32中间输出增大四倍，不能把这些差值说成纯激活耗时，但足够否定“先把尾部拆出去就会快”的这次候选。

## 下一步优先级

1. 在真实ViT展开核上做加载/矩阵调度的受控对照：保留布局、tile、K顺序和输出，分别改变A/B片段提前读取与流水组织；先验证是否能缩小裸矩阵缺口。同步记录寄存器资源和实际时钟。
2. C32只挑一个明确的数据往返改动做等价候选，按真实整网收益验收；输入合并/格式暂存有成本，但不要重做已经更慢的“删掉post half暂存、残差重读”方案。
3. 更深入硬件计数器只用输出已验证的纯HIP路径；之前混合D3D/HIP捕获输出错误的数据继续弃用。现有证据不足以给出DRAM、LDS、指令依赖各自的精确时间比例。

本次新增两组实验共200个计时槽、20次整网原始FP32检查通过；双架构编译，实跑gfx1201。没有新增已采用的生产优化。原始报告继续保留，以上结论不替代各报告的测量限制。

## 22:33后补充：ViT展开/收缩的不对称已有因果证据

[正反对照实验](../vit-schedule-cause-20260921/README.md)：展开传编译期K1024/N4096，让编译器自动四份展开，1080从56.2降至36.2μs；固定尺寸却禁止展开仅约4%改善，动态尺寸只写unroll提示没有改变机器码或速度。反向取消收缩的展开则从36.1升至76.7μs。运算顺序与输出全同，支持循环展开后的读取/地址/指令调度是这对算子差异的主要来源。整网正向900/1080省0.087/0.206ms，观测频率没有升高。此结论不覆盖整网全部差距，也没有给显存等待做精确占比；研究候选尚未部署。

## 22:51后补充：全网筛选后采用三项无损改动

[八组候选与正式回归](../network-fixed-shapes-20260921/README.md)：审计默认路径234调用，分别试固定通道/尺寸/token。采用ViT展开、ViT投影、解码器投影；其余候选收益小或两档不一致，保留实验。正常ABI模块千帧ABBA：900省0.159690ms（1.21%），1080省0.310209ms（1.67%）；96对逐帧RGB及最终模块四次原始FP32输出全同。主线hip/deep_fast.hip已更新，固定的是通道维度，图像宽高仍动态，未改变画质配置。先前报告中的基线已成为本次改动前的历史测量，后续实验请以本次selected-modules为新基线。

## 23:15研究主线校准：算力缺口是核心验证器

用户明确：研究的核心始终是解释算力缺口，提速是结果之一，不能用“又省了几微秒”替代机制认识。

后续每轮记录四件事：当前比较口径与缺口、待验证的具体原因、能区分这些原因的对照、实验后已解释与仍未解释的部分。负优化若能排除一个原因，同样是有效研究；正优化只有耗时变化、没有机制证据，也不能宣布缺口已解释。

近期聚焦改善后的ViT展开：真实尺寸有效吞吐约148TF，与约405TF寄存器峰值之间还有差距。二者的访存和工作条件不同，这个差值是研究问题，不是已经证明可追回的闲置算力。优先控制数据读取/复用、循环调度与并行工作规模，配对记录时钟、输出一致性和生成指令，逐步区分原因。整网收益继续作为工程验收；算力缺口解释作为研究验收。

## 23:16后补充：剩余缺口需要先统一运行条件

[十项调度与前序负载对照](../vit-gap-controls-20260921/README.md)：稳定1080上，4份展开附近继续增加到8/16、合并工作组、双行tile权重重用都没明显提升。900独立热核基线却波动，伴随显存低档；同代码在计时前先做显存搬运，均值与波动明显改变，核心/显存时钟也改变，不能把初扫900的百分比作优化收益。

稳定1080真实核约2.46～2.50GHz，粗略时钟参考约322～328TF，而原405TF寄存器峰值是在约3.11GHz。校正口径后148TF仍约45～46%参考，剩余限制尚待解释。下一优先级是同一launch复制独立工作，查工作规模/填充收尾与重用/并行度的交互。本轮没有新增生产优化。

## 23:37后补充：工作规模不是足够的解释，输入重用成为下一条线索

[同launch复制与输入分离](../vit-work-scale-20260921/README.md)：1080整份排列M1从1→8份，每份36.085→35.166μs，改善有限。交错八份可到31.7μs，M2到30.3，但在同核中把各份输入改为不同地址后，交错收益大多消失（M1 31.613→34.788；M2 30.549→36.567），整份排列则基本不变。数据与输出相同，288槽及6次原始输出全同；部分时钟状态也改变，未作缓存周期占比归因。

剩余缺口不能仅靠增加独立工作解释。下一步在固定尺寸基线上查A输入的片段连续布局，并计入打包成本；不要把批量共用输入的吞吐改善当游戏单帧优化。

## 2026-09-22 00:04补充：连续输入布局未带来整网收益

[固定尺寸行/片段布局对照](../vit-input-layout-20260922/README.md)：1080矩阵只快约2.2%，900持平，打包多约0.48μs；整网3200帧ABBA差仅约1μs，视为持平，不采用。两种布局输出与参考一致，64分项槽及20次原始网络FP32检查通过。

共享输入重用与连续地址不是同一变量，不能因此排除访存。下一步固定逻辑读取量、增加寄存器内矩阵工作，测计算密度曲线；先审指令数及N=1探针干扰，再讨论供数或计算瓶颈。

## 2026-09-22 00:17补充：提高计算密度后可执行约300TF矩阵工作

[固定读取量的密度曲线](../vit-compute-density-20260922/README.md)：经过两次探针校准，最终空控制接近原核；保持20条逻辑加载/K64，矩阵工作1/2/4/8倍，稳定1080约150/177/264/299TF，按各自时钟粗参考从46%到86%。额外指令经ISA确认、原网络输出一致。它表明150TF不是这条真实读取路径上的矩阵硬上限，但包含冗余独立计算、资源/调度变化，不能把差值全归显存，也不能当游戏加速。

下一步试ViT M32×N32平衡tile，在不加冗余工作、不翻倍累加器的条件下，令每K16的A/B逻辑读取5份降为4份，检验有用重用能否兑现。900的独立热核状态仍不稳，归因主看稳定1080，采用仍须整网验证。

## 2026-09-22 12:04补充：平衡tile反而放大分散A读取代价

[ViT平衡tile与A布局交叉对照](../vit-balanced-tile-20260922/README.md)：16×64→32×32仍四累加片段，完整K64加载20→16条、WMMA保持16条；但行布局1080约36→48.5μs。A跨1024字节读取增多，B连续片段减少，逻辑字节更少没有保证更快。将32×32的A改成片段布局后48.7→34.4μs（核心频率还降低），90031.3→24.2；无spill，驻留容量都64wave/MP。支持数据排布与块形状交互，而不是直接测得DRAM或缓存周期占比。

计入打包后热微核组合快4～5%，整网3200帧却90012.777513→12.786306、108017.943379→17.940298ms，视无稳定收益，不采用。144微槽与24次整网原始FP32检查全同。下一具体对照可用同样八累加片段的16×128/32×64，分别重用分散A/连续B，继续区分操作数取数与指令发射组织；原始约45～46%时钟参考的主要缺口尚未填补。

## 2026-09-22 12:40补充：八累加器与少展开仍未兑现稳定整网收益

[16×128/32×64及u4/u2对照](../vit-eight-accumulators-20260922/README.md)：同八组累加片段下，32×64片段A优于16×128，但原行布局未必成立。u4→u2降低VGPR，16×128反而慢，HIP API驻留上限还保持44；32×64上限升56，1080/900收益仍不同。实际HSACO metadata、汇编及hipFuncGetAttribute寄存器数一致，但编译器Occupancy与HIP查询不成简单倍数关系、部分排序不一致，暂不作物理粒度解释。

热打包+矩阵组合可快8～16%，包含时钟变化；整网6400帧的四组变化仅0～0.103%，不足采用。208微槽输出同，40次整网原始FP32同，生产/0.28不改。下一优先级转为真实网络时序下的稀疏段计时，并校准插事件的扰动，先区分小占比与缓存/调度环境差异，不再盲扫tile。

## 2026-09-22 13:19补充：真实时序区间对照与计时精度限制

放大到首次pack→block38末，5120事件读数全部有效：1080 ViT区间2.051730→2.051415ms，9001.272712→1.268393，没有看到热微段那种大幅收益；其他ViT工作稀释、频率/缓存/调度变化仍需分开。标记+逐帧读取使整网wall增加0.070～0.091ms，比候选净差更大，保留无标记基准，不将它当原生开销。两种接受试验112次原始FP32全同，生产未改。下一步考虑真实网络内受控重复的wall放大对照，但其边际时间也不能冒充原生阶段分账。
